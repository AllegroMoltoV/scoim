# ピアノ生成ランタイム設計

この文書は、`solo_piano_3m_v2`のフェーズ3から8で使うLLM呼び出し、作成途中状態、検査、保存、再開、互換性を所有する。公開処理の入口とフェーズ2は[SCoIM初版の公開インターフェース](scoim-public-interface.md)と[SCoIM生成工程](scoim-generation-workflow.md)に従う。

## 入力と出力

入力は、`script-0.4.0`の検証済み楽曲設計データ、[投影台帳](glossary.md#投影台帳)、`solo_piano_3m_v2`の型付き能力、参照目標、実行設定である。出力は、フェーズごとの作成途中状態、`PiecePlan`、共有和声、前景、伴奏、`ScoreSpec`、`PerformanceSpec`、`RenderedPerformance`、MusicXML、SMF、累積投影台帳、診断用SMF、全LLM実行記録である。

設計に対する実装の未完了箇所は[roadmap](../roadmap/scoim-next-generation-path.md)に記載する。

楽曲設計データが指定しない調性、和声、音符、演奏値を、固定値や文書hashから補わない。未決定の音楽値はLLMに選ばせる。ID、参照、順序、相対長、マテリアル配置、楽譜生成単位、楽譜生成単位レイヤー、hash、形式変換はPythonが決定する。

## LLM境界

モデル転送には、オペレーションごとの型付きJSONを使う。公開保存形式とモデル転送形式は同じである必要はない。LLMへ新しい固定IDを発行させない。Pythonが候補へ付けたIDは、二つ目の構成オペレーションで選択と参照に使える。フェーズ2では、最初のモデル操作が非公開の有限語彙で遷移専用区分を明示する。Pythonがその区分と演奏順から有効な遷移候補を列挙し、二つ目のモデル操作は遷移専用区分ごとに候補を一つ選ぶ。任意の三つのマテリアル配置IDを組み立てさせない。JSON Pointer、検査式、実行可能コード、MusicXML、絶対MIDIイベントは返させない。

LLMオペレーションは、全体設計、楽譜生成単位ごとの共有和声、配置役割に応じた楽譜生成単位レイヤーの内容、区分ごとの演奏方法に分ける。一つのレイヤーの内容には、上下両方の声部と、区分内で異なる開始位置と終了位置を持つ音符を含められる。遷移は、前後のマテリアル配置と専用の遷移区分を文脈として、その遷移区分に属するレイヤーを作る。

フェーズ5では、LLMが伴奏音の発音位置、希望音価、和音度数、希望音域、声部、奏法を選ぶ。希望音域は具体音高を限定する絶対条件ではない。Pythonは最初に希望音域内の候補だけで全イベントを探索する。探索上限へ達する前に配置不能と確認できた場合だけ、指定された和音度数と共有和声に一致するピアノ全域へ候補を広げ、希望音域内、同じ声部の移動量、希望音域の中心からの距離、音高の順で安定化する。同一鍵重複や低域間隔を避けるために必要な場合だけ、同じ和音度数を希望音域外へ置く。最初の探索が上限へ達した場合は候補を広げず、探索上限到達として停止する。

演奏オペレーションは、検査済み`ScoreSpec`の完成後に実行する。Pythonが演奏指示の対象と比較元から呼び出し順を作り、生成プロファイルの[演奏要素](glossary.md#演奏要素)と[演奏選択語彙](glossary.md#演奏選択語彙)からプロンプトと応答Schemaを作る。LLMは、演奏指示が指定する演奏要素に対応する登録済みの演奏方法だけを選ぶ。区分ID、任意の数値、未登録の演奏方法、楽譜を変える提案は返さない。Pythonが位置で対象へ対応付け、`scoim.performance_ir.SectionPerformance`と`PerformanceSpec`へ直接変換する。

Pythonは各呼び出しの前に、入力から一意に決まるID、参照、対象範囲、許可語彙、時間容量を確定する。次の要求には、確定済みの上流値と、現在のオペレーションに必要な文脈だけを渡す。プロンプト、モデル応答Schema、事前検査、投影検査は、同じ型付き生成プロファイル能力を入力にする。

使用するモデルと内容修正回数はデータ契約へ固定しない。現在の実装では、汎用的な複数プロバイダー基盤を作らない。これらの設計判断の状態は[決定状態](scoim-decision-status.md)を参照する。

公開生成では、[モデル実行条件](glossary.md#モデル実行条件)を最初のモデル呼び出し前に保存する。各応答でrunnerが記録した情報をその条件と照合し、不一致の応答を採用しない。終了状態など呼出し後に確定する事実はattemptへ保存するが、事前条件として扱わない。

## 作成途中状態

作成途中状態は、検証済み楽曲設計データのhashと、段階ごとに検証済みとなった音楽値を保持する。

- `PiecePlan`
- 楽譜生成単位ごとの共有和声
- 楽譜生成単位レイヤーごとの一つ以上の声部と音符
- 区分ごとの検査済み演奏方法
- `PerformanceSpec`と`RenderedPerformance`
- 値ごとの入力hashと出所

同じマテリアルを別の区分で使う場合も、各マテリアル配置に対応する別の楽譜生成単位レイヤーを作る。変奏関係は、元の対象種類とIDを保った生成要求として渡す。マテリアルIDだけをkeyにして、異なる使用箇所の具体的な音符を共有しない。

値を変更した場合は、その旧hashを読んだ派生値だけを推移的に無効化する。無関係な楽譜生成単位とレイヤーは保持する。同じ差分で依存元と依存先を同時に書き換えず、適用前後のhashを検査する。操作名、段階番号、実行順は音楽データへ保存せず、実行仕様へ置く。

## 下位表現への確定

フェーズ3の全体設計が検査に合格した時点で、Pythonが`PiecePlan`へ変換する。ここで、一つの子区分を持たない区分に一つの楽譜生成単位を割り当て、楽譜生成単位IDと時間容量を確定する。フェーズ3の共有和声、フェーズ4の前景、フェーズ5の伴奏は、この`PiecePlan`を共通の時間基準として使う。

共有和声と楽譜生成単位レイヤーが完成した後は、Pythonだけで`ScoreSpec`へ変換する。各マテリアル配置に一つの楽譜生成単位レイヤーを作り、共有和声は楽譜生成単位に一度だけ置く。共有和声を各レイヤーへ複製しない。

各派生物は隣接する出所だけを参照する。楽譜生成単位は区分、楽譜生成単位レイヤーはマテリアル配置、演奏音符は楽譜音符を参照する。Pythonは投影台帳の参照鎖を全件検査し、検査証拠のない機械対象を`passed`にしない。

楽譜生成単位内の相対時間は共通の整数格子へ写し、丸め、暗黙反復、末尾への無音追加を行わない。共有和声は最後の楽譜生成単位を含めてフェーズ3で確定し、最後の和音が全体の調性の主和音であることを検査する。

フェーズ6は、フェーズ3から5で検証済みとなった和声と楽譜生成単位レイヤーを、そのまま`ScoreSpec`へ構築する。終止用の音符を追加せず、既存音符の音高、開始位置、音価、声部を変更しない。楽譜上の強弱と呼吸は空とし、演奏表現を追加しない。曲末の聴感は診断経路で作った最終SMFの試聴で確認し、主音の長音がないことだけを理由にフェーズ6を不合格にしない。

フェーズ3から5で作った楽譜生成単位、楽譜生成単位レイヤー、楽譜音符の投影証拠は、フェーズ6で同じ対象への別の証拠として複製しない。フェーズ6は累積投影台帳と実際の`ScoreSpec`が一致することを全件検査し、楽曲設計要素の変奏関係とマテリアル配置遷移を楽譜生成条件へ対応付けた新しい証拠だけを追加する。

フェーズ7は、自然言語の演奏指示、各指示の演奏要素、検査済み`ScoreSpec`、生成プロファイルの演奏選択語彙を使う。LLMが選んだ方法をPythonが`SectionPerformance`へ対応付け、指定されていない演奏要素を変更していないことを検査する。すべての区分の値が確定した後に`PerformanceSpec`を一度だけ構築する。`PerformanceSpec`から`RenderedPerformance`を作り、全演奏音符が元の楽譜音符を参照することを検査する。自然言語の達成は`unverified`とし、機械的に確認できないことだけを理由に失敗させない。

フェーズ8は、`ScoreSpec`からMusicXMLを、`RenderedPerformance`からSMFを生成する。試行ID、構成ID、元の構成manifestのbytesとそのSHA-256を来歴として含める。再読込み、hash、来歴、必須ファイルを検査した後に生成試行bundleを確定する。フェーズ8は音符または演奏値を変更しない。

## 検査と内容修正

各LLM応答は、作成途中状態へ適用する前に[検査](glossary.md#検査)する。検査順序と失敗処理は[生成工程の共通検査](scoim-generation-workflow.md#共通の検査と失敗処理)に従う。不合格の場合は、元の依頼、現在分かっている問題、元応答、変更禁止の上流値をLLMへ返し、有限回だけ[内容修正](glossary.md#内容修正)を行う。修正後は同じ検査を先頭から再実行する。創作上の目標が意図どおりに聞こえたかを自動判定できないことは、内容不合格に含めない。

内容修正で変更できるのは、そのオペレーションが所有する値だけである。認証、timeout、quota、応答欠落は内容修正の対象にしない。自動フォールバックは行わず、上限または改善停止に達した場合は型付き失敗で終了する。修正回数、再提出範囲、自動フォールバックに関する設計判断の状態は[決定状態](scoim-decision-status.md)に従う。

## 保存と再開

runの入力、モデル要求、raw応答、検査、修正要求、修正応答、再検査、確定差分、成果物を上書きせず保存する。各attemptには、応答bytesのSHA-256、その応答に対する検査結果、検査で見つかった問題を保存する。採用記録は、採用したattemptの相対pathと応答hashを持つ。通信なしの検証では、採用記録、attemptの検査結果、保存済み応答が同じ応答を指し、採用した検査結果が合格であることを確認する。作業中状態は保存済みeventから再構築でき、別プロセスから再開できなければならない。

公開v2生成の出力ルートは、入力内容hash、生成profile、構成ID、試行ID、モデル実行条件を持つ不変な`public-run.json`で識別する。一時的な兄弟directoryへ識別記録を書き、directory単位で出力ルートへ確定配置してからモデルを呼ぶ。同じ識別情報を持つ既存出力だけを再開し、各フェーズの専用loaderで完成状態を検証する。検証済みの完成フェーズは再利用し、最初の未完成フェーズから続行する。

モデル呼び出しの終了状態が不明なattemptは自動再試行しない。異なる入力、profile、ID、モデル実行条件、または改変された完成フェーズを同じrunの続きとして受け入れない。

決定的なフェーズの成果物と確定bundleは、最終保存先と同じ親の一時ディレクトリへ作る。入力、出力、累積投影台帳、診断用SMF、状態、hashを再読込みし、必須ファイルと再構築結果を確認した後、ディレクトリ単位で最終名へ変更する。既存の完成物を上書きせず、再開時は検証して再利用する。

結果は次を分けて持つ。

- 処理の終了状態: 完了、失敗、中断
- 成果物の用途: なし、診断専用、候補
- 型付きの問題

診断専用成果物を正式候補へ昇格させず、失敗したフェーズrunを後続入力にしない。

## 診断用SMF

[前景](glossary.md#前景)確定後と楽譜確定後に、Pythonだけで診断用SMFを保存する。通常生成を停止せず、最終SMFに問題があった場合だけ原因を遡るために使う。後続生成の入力や候補順位には使わない。楽譜確定後の診断用SMFは再読込みし、楽譜にある全音符の音高、開始、終了、声部が中立演奏へ過不足なく写されていることを検査する。不合格の場合はフェーズ6を完了扱いにしない。この方式の設計判断の状態は[決定状態](scoim-decision-status.md)を参照する。

## 互換性

`solo_piano_3m_v2`は、`script-0.4.0`と新しい下位表現だけを受理する。公開CLIの新規生成ではv2を既定値とし、`solo_piano_3m_v1`は明示指定する互換経路として残す。旧Schema、旧workspace、旧bundleの意味を変更しない。生成試行bundleの通信なし再生はmanifestの版に従い、CLIの既定profileで旧bundleの意味を変更しない。

新しい生成経路で旧名と新名の両方を受理する互換分岐を作らない。版の変換が必要な場合は、元記録を残したまま新しいrunとして明示的に行う。
