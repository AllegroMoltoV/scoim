# ピアノ生成ランタイム設計

この文書は、`solo_piano_3m_v2`の実現試行で使うLLM呼び出し、生成順、検査、保存、再開、互換性を所有する。公開処理の入口と構成生成は[SCoIM初版の公開インターフェース](scoim-public-interface.md)と[SCoIM生成工程](scoim-generation-workflow.md)に従う。

## 入力と出力

入力は、`script-0.4.0`の検証済み楽曲設計データ、投影台帳、生成プロファイルの型付き能力、参照目標、実行設定である。新規生成の順序を`phase3 → score → phase7 → bundle`とする。`phase3`が構成と共有和声、`score`が全音符と`ScoreSpec`、`phase7`が演奏、`bundle`が最終成果物を所有する。処理の区切りとオペレーション数は一対一ではない。

出力は、作成途中状態、`PiecePlan`、共有和声、`ScoreSpec`、`PerformanceSpec`、`RenderedPerformance`、MusicXML、SMF、累積投影台帳、診断用SMF、全LLM実行記録である。データの意味は[用語集](glossary.md)、楽譜値の契約は[楽譜設計](solo-piano-score.md)に従う。

楽曲設計データが指定しない音楽値を固定値や文書hashから補わない。フェーズ3の新規runでは、Pythonが主音を0から11までの整数から等確率で一度だけ選び、不変なrun仕様へ保存してからモデルを呼ぶ。LLMが長調・短調、譜面時間量、和声、音符、演奏方法を選ぶ。PythonがID、参照、順序、時間換算、音高配置、hash、検査、保存、形式変換を担当する。

## 全体計画と共有和声

フェーズ3の全体設計には、保存済み主音、希望演奏時間、基準`divisions`、全区分のID・親ID・兄弟順・役割・説明、葉の演奏順、変奏関係を渡す。LLMが長調・短調、曲全体の和声の流れ、区分ごとの和声意図、`total_score_units`を返す。Pythonが元の相対長を保持した`PiecePlan`と量子化済み時間容量を作る。内容修正でも保存済み主音を使う。

共有和声は楽譜生成単位ごとに作る。局所要求には対象区分の祖先説明、採用時間容量、全体設計を渡す。区分変奏の対象に含まれる場合、関係の種類とID、説明、保持要求、変更要求、元区分の全葉と確定済み共有和声を加える。区分変奏の元範囲が先範囲より前にある条件に従い、必要な元和声をそろえてから対象を生成する。複数祖先から適用される関係をすべて渡す。

最後の楽譜生成単位を含め、共有和声を音符生成前に確定する。最後の和音を全体の調性の主和音にする。0unitの区分を削除・延長して補わず、全体設計の有限修正へ返す。量子化の契約は[構成比と音符時間格子](solo-piano-score.md#構成比と音符時間格子)に従う。

## 楽譜の生成計画

`score`段階では、比較に必要な音符の依存関係から[共同生成群](glossary.md#共同生成群)と実行順を決める。

1. 区分変奏の対象範囲に含まれる全マテリアル配置を一つの群へまとめる。対象範囲が重なる群を結合する。残る配置を単独の群とする。
2. 区分変奏の元全配置から先全配置、明示的なマテリアル・配置変奏、同一マテリアルの暗黙再利用、遷移の前後境界、同じ楽譜生成単位の占有順を依存として記録する。
3. 相互に依存する群を、依存グラフの強連結成分として結合する。結合後の群を安定した依存順へ並べる。
4. 全配置を一回ずつ生成対象へ含め、すべての関係を計画へ対応付ける。部分的な順序だけを成功として返さない。

群の結合で台本の区分や配置を変更しない。生成・修正・確定の範囲だけを決める。型付き能力が扱う関係の範囲は[生成プロファイル](controllable-composition-system.md#v2の生成能力)に従う。既存構成bundleから新しく生成する場合も、モデル呼び出し前に現行の生成計画と能力を検査する。保存済み構成の能力snapshotを書き換えない。

## 共同生成の要求と応答

群の要求には、対象配置を役割別の安定順で列挙する。各対象の説明、祖先説明、共有和声、時間容量、群外で確定済みの占有音符を加える。遷移前景には担当遷移のID、説明、元・遷移専用・先の配置IDと前後の境界を渡す。内容修正にも元の要求を保持する。曲末を含む要求には、最後の共有和声、終端を導出する役割の全配置、伴奏の支持担当配置を加える。担当配置の群外確定と群内候補を明示し、全担当が採用済みの場合だけ具体的な共有終端を渡す。

区分比較には、元・先それぞれの全葉、累積位置、採用済み長さ、全配置、共有和声、関係の原文を使う。子区分数、長さ、配置役割の一致を必須にせず、子同士の一対一対応を作らない。元伴奏から対象前景への引継ぎや、対象から伴奏を取り除く変奏も扱う。

群外の比較元には、確定済みの全音符と内容hashを渡す。群内の比較元には、同じ応答で共同提案する対象と関係を明示する。群内の未確定伴奏は記号イベントであり、要求時点で最終具体音高を配達済みと記録しない。確定比較と共同候補を要求・検査証拠で区別する。

モデル応答は`foregrounds`と`accompaniments`の位置対応配列とする。要求で役割別の配置順と件数を固定し、モデルに新しいIDを発行させない。各前景が具体的な`notes`を持ち、各伴奏が和音度数・希望音域・時刻・音価・声部・奏法による`events`を持つ。配置への対応付けと音符IDの付与はPythonが行う。

## 共同伴奏の音高配置

まず群内の前景候補をすべて検査する。その後、同じ楽譜生成単位にある群内の未確定伴奏を共同探索し、群外の確定音符と前景候補との衝突を検査する。未確定伴奏を配置別に順次固定し、後の配置の解を失う方式を使わない。

探索するイベントには元配置と元indexを対応付ける。同一配置の再打鍵だけに、既存の音価短縮規則を適用する。異なる配置のイベントを、同じ配置内の連続音として短縮しない。

最初に全イベントを希望音域内だけで探索する。探索上限へ達する前に解なしと確認できた場合だけ、同じ和音度数と共有和声に一致するピアノ全域へ候補を広げる。希望音域内、同じ声部の移動量、希望音域の中心からの距離、音高の順で安定化する。探索上限到達と配置不能を区別し、前者を理由に探索範囲を広げない。和音度数、ピアノ音域、同一鍵重複、低域間隔の条件を両方の探索で維持する。

旧完成bundleの再検証では、保存時の配置別の音高配置規則を使う。共同探索へ置き換えて音高を変えない。

## 検査、修正、確定

各群の候補を、Schema、位置対応と網羅、前景音符、暫定共有終端、伴奏イベント、共同音高配置、配置後の終端保持、参照、変奏、投影の順に検査する。終端の導出と支持条件は[楽譜設計](solo-piano-score.md#曲末)に従う。全終端担当がそろった時点で導出し、後続の支持担当がまだないことだけを理由に途中群を拒否しない。終端と群候補を同時に確定し、群外の確定値を変更しない。区分全体の完全コピー検査は[楽譜設計](solo-piano-score.md#再利用変奏対比遷移)に従う。群外の確定値と群内候補の全対象を使い、対象全体がそろった同じオペレーションで比較する。

前景の占有検査では、同じ音高かつ同じ声部の半開区間が重なる場合だけを衝突とする。区間の境界が接する場合と、異なる音高・声部の同時発音を許す。検査結果へ候補のindexと区間、衝突相手の区間を記録する。群外の確定占有音符を初回要求と内容修正で固定し、群内候補どうしの衝突も検査する。Pythonが候補音符を自動移調・移動・短縮して検査へ合わせない。

内容不合格では、元の要求、候補全体、問題、変更禁止の群外確定値を渡し、群全体を有限回だけ修正する。群の一部だけを採用せず、全検査の合格後に一括確定する。上流の確定済み群、構成、共有和声を書き換えない。修正後も同じ検査を先頭から実行する。上限まで不合格が残る場合、後続群へ進まず型付き理由で終了する。

自然言語の保持・変更要求の達成を、形式的な配達や完全コピー検査の合格から推測しない。機械で検査できない創作目標を`unverified`として保持する。認証、timeout、quota、応答欠落、モデル実行条件の不一致を内容修正の対象にしない。自動フォールバックを行わない。

全群の確定後、Pythonが共有和声と全音符から`ScoreSpec`を組み立てる。音符を追加・削除・変更せず、楽譜上の強弱と呼吸を空にする。音符と累積投影台帳の全件一致を検査する。共有終端を完成状態へ保存し、採用応答から再構築した終端と完成楽譜から導出した終端を照合する。区分変奏について、要求した関係・比較範囲・比較内容hash、採用候補、完成楽譜の対応を再導出して照合する。端点のID一致だけを配達証拠として扱わない。

## 演奏と最終成果物

フェーズ7は、完成した`score`の検証済み`ScoreSpec`、共有終端、そのhashと演奏指示を入力にする。指示の対象と比較元から演奏オペレーション順を決め、対応する演奏要素の有限語彙だけをLLMへ渡す。選択field、対象、能力を検査し、全応答の合格後に`PerformanceSpec`を作る。指定されていない演奏要素や楽譜値を変更しない。

Pythonが同時同鍵を打鍵グループへまとめ、`RenderedPerformance`へ変換する。全楽譜音符の過不足ない参照、同一鍵の非重複、値域、決定性と、[共有終端の保持](solo-piano-performance.md#共有終端の保持)を検査する。同時同鍵の候補でvelocityが異なる場合、型付き`unrepresentable`で停止する。演奏変換の不合格をLLMの内容修正へ戻さない。演奏指示の知覚上の達成を`unverified`として記録する。

最終bundle処理はLLMを呼ばない。`ScoreSpec`からMusicXML、`RenderedPerformance`からSMFを作り、再読込み、hash、来歴、必須ファイルを検査する。元の構成manifestのbytesとSHA-256を保存する。音符または演奏値を変更しない。

完成bundleの再生先は、[公開インターフェースの出力先契約](scoim-public-interface.md#cli)に従って、書込み前に検査する。

## 保存と再開

現在の時間契約を`quantized-score-v1`、生成文脈契約を`section-range-context-v1`とする。公開run識別記録、フェーズ3の不変仕様と和声計画、`score`の不変仕様、フェーズ7の不変仕様で生成文脈契約を照合する。旧契約または契約欠落を新規生成の続きとして受理しない。

公開出力ルートは、入力内容hash、profile、構成ID、試行ID、モデル実行条件、時間契約、生成文脈契約、ペダル契約、終端契約`shared-terminal-v1`を持つ版6の`public-run.json`で識別する。一時的な兄弟directoryへ記録して検査し、directory単位で確定配置してからモデルを呼ぶ。同じ識別情報を持つ出力だけを再開する。各応答のprovider、model、model settingsを事前のモデル実行条件と照合する。

`score`版2の不変仕様には入力hash、全群と依存、安定した実行順、修正・探索の上限、終端契約`shared-terminal-v1`を保存する。群snapshotには同じ候補から導出した共有終端を保存し、導出前の群では`null`とする。完成状態には終端値とhashを保存する。モデル要求、応答、検査、修正、採用記録、成果物を上書きしない。採用記録は一次証拠として、採用attemptの相対pathと応答bytesのSHA-256を持つ。

有限内容修正の新しい記録は、元応答がJSON objectの場合にcanonical JSONのSHA-256を持ち、それ以外の場合に元応答bytesのSHA-256を持つ。初回と再開で同じ定義を使う。旧再開処理で元応答bytesのhashを保存した既存の修正記録も、元応答とhash、修正方針、検査結果が一致する場合だけ保持して使う。修正記録の保存後、修正attemptの予約前に中断した場合も、既存記録を照合して残る1回の修正へ進む。attempt、検査結果、採用記録の応答hashには引き続き元応答bytesを使う。

再開と完成loaderは、保存済み採用応答から同じ候補検査を実行し、群の音符と投影証拠を再構築する。採用応答の再呼び出しを行わず、状態の保存前後や完成楽譜の保存前で中断しても、確定済み群を復元する。要求、比較内容、候補、台帳の欠落・改変・差替えを拒否する。終了状態が不明なattemptを自動再試行しない。

全配置の部分的な採用状態を完成群と扱わない。群の確定を原子的に扱い、決定的成果物と完成bundleも同じ親directoryの一時領域へ作る。保存物を再読込みして検証した後、directory単位で最終名へ変更する。既存の完成物を上書きしない。

新しい生成試行bundleのSchema版を7とし、`phase3`、版2の`score`、版5の`phase7`の実行記録を持つ。フェーズ7の版5に終端契約`shared-terminal-v1`、ペダル契約`harmony-release-attack-v1`と語彙版`0.2.0`を対応付ける。フェーズ7の入力、run仕様、完成状態で共有終端の内容hashを照合する。段階の欠落、別の上流への差替え、契約の混在を検査する。旧フェーズ4・5・6の状態を新経路の中間物として作らない。

採用attemptには`completed`の終了記録を必須とし、終了記録、検査結果、採用記録の応答hashを実際の応答bytesへ照合する。完成工程では保存済みのオペレーション一覧と採用記録の集合を照合し、欠落と余分な採用を拒否する。モデル操作を持たない工程に採用記録を要求しない。不採用の失敗履歴を理由に完成試行を拒否しない。bundleの作成と通信なし検証でも同じ採用条件を使う。

bundle内の全工程に完成状態と必須保存物を要求し、上流の出力と下流の入力、各工程の楽曲設計データを照合する。旧フェーズ4〜6経路にも保存済みJSONの一致検査を適用する。現在の生成規則で旧音符を作り直さない。構成manifestに保存された楽曲設計データの内容hashを使用データへ照合し、新規bundleではそのhashを必須とする。旧版1〜5のhash欠落は許容する。

公開runの完成bundleを再利用する場合、bundle単体の検証に加え、現在の構成ID、試行ID、構成manifestのbytes、完成した各工程の保存ファイルと照合する。単独で正常な別試行のbundleも、現在のrunに一致しなければ再利用しない。

## 診断用SMF

`score`段階は、全音符の確定後に前景のみの診断用SMFと全楽譜の診断用SMFを作る。各診断を中立演奏へ変換し、対象音符の音高、開始、終了、声部が過不足なく対応することを再読込みで検査する。不合格なら`score`を完了扱いにしない。

診断生成のために通常処理を中断しない。診断用SMFを後続生成の入力や候補順位に使わず、最終SMFに問題があった場合の調査へ使う。公開結果の診断artifactキーを維持し、保存先を新しい`score`段階へ対応付ける。

## 互換性

旧版1〜6の完成bundleを、保存時の時間・生成文脈・演奏変換・操作順・音高配置の規則で検証し、同じMusicXMLとSMFへ再演奏する。フェーズ7の版1〜3には旧ペダル契約と語彙版`0.1.0`を適用する。bundle版3にはフェーズ7版2、bundle版4・5にはフェーズ7版3、bundle版6にはフェーズ7版4、bundle版7にはフェーズ7版5とscore版2を要求する。bundle版5・6のscore版1は、終端契約を追加せず保存時の要求・候補・snapshotを再構築する。フェーズ7版4のペダル契約は維持し、共有終端の保持を遡及適用しない。旧操作順で記録した台帳へ新しい群順を適用しない。旧版を新しい版へ暗黙に包み直さない。

旧途中runの続行と旧完成段階から新しい後続段階への混在を拒否する。保存済み構成bundleから、新しい出力先と試行IDで実現試行を始める。新しい生成で旧名と新名の両方を受理する互換分岐を作らない。

`solo_piano_3m_v1`を明示指定する互換経路と、旧Schemaの完成bundle再生を維持する。未知の版をfield構成から推測しない。結果には完了・失敗・中断、成果物用途、型付き問題を分けて持ち、診断専用成果物を正式候補へ昇格させない。
