# SCoIM 楽曲台本契約

この文書は、[楽曲台本](glossary.md#楽曲台本)のデータ契約を定める。利用者は楽曲台本を修正して承認し、内部ID、和声検査、MIDIイベントは確認しない。一つの楽曲台本は一つの[編成](glossary.md#編成)専用にする。設計判断の状態は[決定状態](scoim-decision-status.md)を参照する。

- 設計版: 1.3
- 最終更新: 2026-09-13

## 結論

[楽曲台本](glossary.md#楽曲台本)を、人間が承認する音楽構想の正本とする。内部ID、和声検査、MIDIイベントなど、人間が判断する必要のない詳細は含めない。

同じ楽曲台本から編成だけを差し替えない。

## 文書の役割

楽曲台本は、次を結ぶ。

1. 利用者が入力した「明るい感じのピアノ曲」のような短い依頼
2. LLMが提案する、人間向けの曲全体の流れ
3. 人間による修正と承認
4. 機械用の楽曲設計データへの変換

承認後の楽曲台本は変更しない。内容を変える場合はrevisionを増やし、改めて承認する。

## 論理データ

論理データは次の構造を持つ。

```text
FlowDocument
├── document_type: flow
├── schema_version
├── document_id
├── revision
├── status: draft | approved
├── approval
│   └── content_sha256
├── title
├── overall_flow
├── instrumentation
├── target_duration
└── scenes[]
    ├── scene_id
    ├── name
    ├── length_class
    ├── heard_as
    ├── relation_to_previous
    └── transition_to_next
```

現在の文書形式は`document_type = "flow"`、`schema_version = "0.1.0"`とする。文書種類と版は別々に検査し、項目の有無から文書種類を推測しない。

各項目の意味は次のとおりである。

- `title`: 曲を識別するための題名
- `overall_flow`: 曲全体で何が始まり、どう変わり、どう終わるか
- `instrumentation`: この曲の編成。一文書につき一つ
- `target_duration`: 希望する演奏時間
- `scene_id`: 改訂間で対応を追える安定ID
- `name`: 利用者が場面を指し示すための短い名前
- `length_class`: 場面の長さを厳密な小節数ではなく、短い、中くらい、長いなどで示す値
- `heard_as`: その場面がどう聞こえるべきか
- `relation_to_previous`: 初登場、再現、変奏、対比など、前に出た音楽との関係
- `transition_to_next`: 次の場面へどう聞こえて移るか。最後の場面では、どのように閉じるか

`transition_to_next`は、利用者が聞き分けられる流れを表す文章である。独立した短い区分を必ず挟むという構造指定ではない。楽曲設計データを作るときは、この文章を区分やマテリアルの説明へ渡す。独立した遷移区分が音楽上必要で、構造提案にその区分がある場合だけ、[マテリアル配置遷移](glossary.md#マテリアル配置遷移)を作る。

初回提案時の`document_id`と`scene_id`はPythonが発行する。場面IDは提案順に`scene-001`、`scene-002`のように割り当て、LLMには作らせない。JSON Patchによる改訂では、意味が同じ場面のIDを維持する。

## 人間が判断する範囲

利用者は、次だけを確認する。

- 曲全体の流れが依頼に合っているか
- 場面の順序と大まかな長さがよいか
- 繰り返し、変奏、対比が意図に合っているか
- 次の場面への移り方がよいか
- 編成と希望演奏時間が正しいか

公開操作`show`は、指定した場面、その演奏順、直前の場面、直後の場面を返す。先頭に直前の場面はなく、末尾に直後の場面はない。文書に書かれていない関係を推測して補わない。

利用者には、内部の楽曲設計データ、ID参照、親子関係、JSON Pointer、検査式、モデル応答を確認させない。

## 提案、修正、承認

LLMによる初回提案は、利用者へ提示する前に機械検査する。応答Schemaの不合格が既存のscalar fieldの置換だけで直せる場合に限り、LLMへ追加1回の局所修正を求め、同じ検査を先頭からやり直す。具体的な条件と失敗処理は[生成工程](scoim-generation-workflow.md)を正本とする。

利用者による改訂は、公開`apply`操作でJSON Patchを適用する。現在の公開CLIは、利用者の修正指示からLLMに改訂案を作らせない。改訂後は文書全体を検査し、revisionを増やした新しいdraftとして保存する。人間が承認した内容のhashを`approval.content_sha256`へ保存し、承認後の内容と照合できるようにする。

内容hashは、RFC 8785で正規化した`document_type`、`schema_version`、`document_id`、`revision`、`title`、`overall_flow`、`instrumentation`、`target_duration`、`scenes`のSHA-256とする。`status`と`approval`はhash対象から除外する。ファイル全体のbyte hashとは別物として扱う。

## 楽曲設計データへの変換

公開`solo_piano_3m_v1`では、承認済みの楽曲台本から[楽曲設計データ](scoim-script.md)を作るためにLLMを1回呼ぶ。内容不合格の場合は、同じSchemaで応答全体を追加1回だけ作り直す。

`solo_piano_3m_v2`では、二つのLLMオペレーションと、その間の決定的処理を使う。最初のLLMオペレーションは、区分、マテリアル、各マテリアル配置の役割を提案する。同じマテリアル候補を複数の配置から参照することで、そのマテリアルの再利用もこの時点で決める。最終IDと相互参照は返さない。

Pythonは提案へ安定IDを付け、選択した生成プロファイルの能力で検査する。二つ目のLLMオペレーションは、Pythonから渡された候補と、すでに決まった再利用を変更せず、変奏、遷移、自然言語の演奏指示を提案する。この要求には、生成プロファイルが扱える[演奏要素](glossary.md#演奏要素)と平易な説明も含める。

演奏指示には対象、説明、一つ以上の演奏要素、必要な場合は比較元を含める。演奏指示は楽譜を変えずに調整できる弾き方だけを扱い、音域、旋律、伴奏音、和音の要望を複写しない。それらの要望は区分とマテリアルの説明からフェーズ3から5へ渡す。知覚上の特徴名や検査式への変換も行わない。上流の構造では必要な関係を表せない場合は、関係を捏造せず`structure_insufficient`を返せる。この場合は局所的な内容修正を行わず、現在の構成試行を失敗として保存する。Pythonが参照を構築し、完成した楽曲設計データを検査する。正確な呼び出し順と内容修正は[生成工程](scoim-generation-workflow.md)を正本とする。

変換時には、題名、全体の流れ、場面の順序、長さ、聞こえ方、前との関係、次への遷移、編成、希望演奏時間を[投影台帳](glossary.md#投影台帳)へ登録する。台帳のデータ契約は[楽曲設計データの下位投影](scoim-script.md#下位投影)を正本とする。

順序、長さ、対応関係、編成、時間のように構造化できる事項はPythonで検査する。自然言語で書かれた音楽的な意図は、その意図を実現するpromptへ欠落なく渡ったことだけを機械検査し、音として達成したかは`unverified`とする。配達先がない事項は`unrepresentable`とし、楽曲設計データを`validated`にしない。

## 正規化と識別

- `document_id`は楽曲台本を識別する。
- `revision`は同じ楽曲台本に対する人間向け改訂を識別する。
- LLMによる表記揺れの正規化と内容hashの計算はPythonが行う。
- 承認済み文書は不変とし、変更は新しいrevisionへ分ける。
- 同じ承認済み楽曲台本から別の楽曲設計データを作る場合は、楽曲台本のrevisionを変えず、新しい`composition_id`を使う。

## この文書が所有する条件

- 人間が承認する正本は[楽曲台本](glossary.md#楽曲台本)である。
- 楽曲設計データは人間へ承認させない。
- 一つの文書は一つの編成専用である。
- 承認済み内容を暗黙に書き換えない。
- 自由記述から下位IDやMIDIイベントを直接作らせない。
