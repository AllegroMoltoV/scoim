| 項目 | 内容 |

## 目的

参照 SMF を現在の生成工程と逆方向へ分解し、生成用中間表現が既存曲を説明できるかを検証する。

SMF から作曲者の元の意図を一意に復元できるとは扱わない。直接観測できるイベント、演奏分析用の派生情報、複数あり得る楽譜と構成の仮説を分ける。

この文書が扱う観測と仮説は、SCoIM の楽曲台本の正本ではない。参照 SMF から得た区分、素材、変奏、演奏意図の候補を、証拠のない確定 field として`scoim.Script`へ書き込まない。SCoIM 全体は`scoim-system.md`、楽曲台本契約は`scoim-script.md`に従う。

## 非ゴール

- 参照曲の元譜を正解として復元すること。
- 最高音を常に主旋律、最低音を常に左手と決めること。
- 固定窓の境界を A、B、フレーズの正解へ変換すること。
- 生の全 note 列を上位層へ残して循環一致させること。
- 一曲に適合した規則を作風全体の規則として採用すること。

## 逆分解と正方向の関係

```text
参照 SMF
    ↓
ObservedSmf
    ↓
ObservedPerformance
    ↓
ScoreTimingHypothesis
（楽譜時間候補と演奏時間候補の組）
    ↓
TextureAndVoiceHypothesis
    ↓
LineAndHarmonyHypothesis
    ↓
MaterialGraphHypothesis
    ↓
FormHypothesis
```

仮説層は、検証後も元曲の正解とは呼ばない。正方向へ戻す場合は候補アダプターを介し、PiecePlanCandidate、ScoreSpecCandidate、PerformanceSpecCandidate として現行レンダラーへ渡す。アダプターが補った既定値は推定値と分ける。

## ObservedSmf

### 責務

SMF の意味を解釈する前の証拠を保持する。

- SMF format、ticks per beat、track 数
- track index、event index、絶対 tick、同じ tick 内の順序
- channel message の型と全フィールド
- meta message の型と全フィールド
- SysEx data
- 元ファイルと正規化 event ledger の SHA-256

note-on と note-off の対応、主旋律、声部、和音、ペダル句はこの層で確定しない。

### イベントの状態

各イベント種別を次のいずれかへ分類する。

- `preserved`: event ledger と診断用 SMF の往復で意味を保持する。
- `derived_only`: 生イベントは保持するが、演奏分析では派生情報だけを使う。
- `unsupported`: 現行処理で保持できず、曲名、件数、理由を損失台帳へ記録する。

`unsupported` が一件でもあれば完全イベント往復を不合格にする。演奏分析対象の特徴往復は別の結果として返せるが、完全往復へ読み替えない。

## ObservedPerformance

ObservedSmf から、演奏分析に必要な情報を派生する。

- tempo map を適用した絶対時刻
- note-on と note-off の対応候補
- 音高、velocity、実音長、channel
- CC64 とほかの演奏用 channel event
- 30 ms 発音群ビュー

30 ms 発音群は、最初の note-on から 30 ms 以内を一群にする既存の版付き診断である。連鎖結合せず、元の発音時刻を変更しない。生観測、SMF 往復、note 対応の正解には使わない。

複数 track、同じ channel、同じ pitch の note が重なる場合、note-off の対応は一意でないことがある。対応候補と調査不能を保存し、任意の FIFO 対応を観測事実にしない。

## 上位仮説の情報制限

上位仮説は根拠となる event ID を参照できる。ただし、ObservedSmf の全イベントまたは ObservedPerformance の全 note を、別名の配列として複製してはならない。

各仮説は次を持つ。

- `status`: `assessed`、`unable_to_investigate`、`unsupported`
- `confidence`: 算出根拠を持つ場合だけ指定する
- `evidence_event_ids`
- `alternatives`: 同じ証拠から成立する別候補
- `assumptions`: SMF にない情報を補った規則

仮説層の型、保持情報、禁止情報は、その段階を実装する前に本書へ追加する。

## 演奏時間の同定可能性実験

### 目的

SMFから楽譜より先に演奏仮説を作れるかを検証する。元のPerformanceSpecを一意に当てることは要求しない。楽譜が未知でも、生成に再利用できる有限の候補集合または楽譜時間に依存しない特徴を、全note列の複製なしで保持できるかを判定する。

### KnownScoreTimingEvidence

採用前の実験型であり、既知のPiecePlanとScoreSpecを持つ対照だけで使う。

- 楽譜上の発音位置
- 対応するObservedSmfのevent ID候補
- 共有開始時刻のアンカー規則
- アンカー規則ごとの共有開始時刻候補と局所残差
- アンカーを変えても不変な同時発音内の時刻差
- note対応と発音位置対応の状態
- 同じ観測を説明する代替対応
- note-on、note-off、CC64の評価状態

共有時刻と局所残差には基準点の自由度がある。共有時刻へδを足し、同じ位置の全残差からδを引いても観測時刻は変わらない。このため、最小値、中央値などのアンカーを仮定として明示し、アンカー依存の値とアンカー不変な差を分ける。

note-offはarticulation、CC64はpedal profileと交絡する。note-onだけの結果、articulationを固定してnote-offを加えた結果、pedalを固定してCC64を加えた結果を別々に返す。

### TimingIdentifiabilityResult

採用前の実験型であり、次を持つ。

- `status`: `identifiable_within_candidate_space`、`equivalent_candidates`、`outside_candidate_space`、`unable_to_investigate`
- `score_known`
- `candidate_space_id`と候補空間のSHA-256
- 表記上の候補数と演奏意味上の候補数
- `semantic_equivalence_id`
- 候補の要約
- 根拠event ID
- 仮定
- 再構成差

`identifiable_within_candidate_space`は、版付き候補空間の中で演奏意味が一つに定まった状態だけを指す。一般の単調時間写像に対する唯一性を意味しない。候補空間に真の演奏がない状態を、調査不能へ混ぜず`outside_candidate_space`とする。

### 演奏意味上の正規形

表記が異なっても、同じPiecePlanとScoreSpecから同じnote-on、note-off、CC64、node intervalを生成する指定は、演奏意味上の同値候補としてまとめる。現行語彙には少なくとも次の既知同値がある。

- `coordination_profile=score`と`aligned`
- `timing_profile=neutral`の`subtle`と`moderate`
- `narrative-v1`で曲全体へ一様に指定し、全体長の正規化で相殺される時間倍率

元DSLの復元評価では別表記として数え、演奏意味の復元評価では一つの同値類として数える。どちらの候補数かを明記せず「一意」と報告しない。

現行`rolled`実装は、同時発音を最低音から最大45 msでずらす。45 msは現行方式の固定値であり、正方向設計にある60 msは新規方式を含む許容上限である。保存済み成果物の互換評価では45 msを使う。

### 直列段階を維持する条件

非同定性があることだけでは、PerformanceHypothesisを先に置く直列順序を棄却しない。次をすべて満たす場合は、代替候補を持つ直列段階を維持できる。

- 候補数が入力note数に伴って実用不能に発散しない。
- 対象とする演奏特徴を正方向へ再構成できる。
- 同じ楽譜候補へ別の演奏候補を適用する部品交換ができる。
- 上位層へ全イベント列または全note列を複製しない。
- 楽譜に依存する値と、楽譜候補が変わっても不変な値を区別する。

これらを満たせない場合は、楽譜時間候補と演奏時間候補を組にした連成仮説へ変更する。結果を確認する前に、連成層を採用済みの正本型へ昇格しない。

### 実験結果と採用判断

既知のPiecePlanとScoreSpecを持つ保存済み6例では、note-onを楽譜位置へ6例すべて対応付けられた。5例は同じ校正曲の改版であり、独立した5曲への一般化証拠には数えない。残る1例では、45 ms以内の局所打鍵差も共有時刻と分けられた。

一方、楽譜が未知の場合は、同じ観測時刻を説明する楽譜位置と単調時間写像の組が無限に存在する。候補を有限にするには先に楽譜格子を仮定する必要があり、演奏時間写像だけでは再構成も別の楽譜への部品交換もできない。これは単に元の演奏意図が一意でないという問題ではなく、直列段階の成立条件を満たさない問題である。

この結果から、`PerformanceHypothesis`を楽譜より先に確定する案は採用しない。次段階は、次の情報を組にした`ScoreTimingHypothesis`の候補集合として扱う。

- 発音の楽譜位置候補
- 楽譜位置から観測時刻への共有時間写像候補
- 同じ楽譜位置に属する発音間の局所時刻差
- 候補を支えるObservedSmfのevent ID
- 仮定、未対応、同値候補

この段階でも、生の全note列を複製してはならない。候補数の上限、表現、抽出法は未決定であり、複数曲を使う次の反証実験で決める。

## ScoreTimingHypothesis開発パイロット

### 開発標本と保留標本

候補抽出方式を一曲へ合わせないため、参照232曲の観測特徴だけで開発標本を固定する。新しい平坦化距離を作らず、検証済みの`profile_distances`が返す`performance_texture`、`rhythm_time`、`pitch_harmony`の三距離を使う。

最初の開発曲は検証済みの実在medoidとする。以後は、選択済み集合までの群別最小距離を求め、その三値の最小値、中央値、最大値が大きい順、最後にcasefold済み曲名順で8曲まで選ぶ。copy fingerprintの完全一致だけを同じ分割へ置く。部分類似とファイル名系列は診断に残すが、同一作品とは断定しない。

保留曲は開発方式を固定するまで選択も保存もしない。開発runnerは8曲だけを置いたstaging directoryと、そのmanifestだけを受け取る。参照コーパスrootや保留選択規則を引数に持たせない。

### 実験型ScoreTimingHypothesisV0

採用前の実験型であり、次を持つ。

- `status`: `candidate`、`outside_candidate_space`、`unable_to_investigate`
- `search_status`: `complete`、`not_converged`
- 観測元のledger SHA-256
- 発音群規則、楽譜格子、共有時間写像の候補ID
- 発音群IDと累積楽譜位置の対応
- 最大9節点の単調な共有時間写像
- 非ゼロの局所打鍵差を持つ発音群の参照
- 全体音価倍率などの同値正規化
- 仮定と根拠event ID
- note-on再構成差、伏せた発音の補間差、語彙数、節点数、局所例外数、正規化後の直列化サイズ

発音群の対応には音高、velocity、note-off、CC64を複製しない。共有時間写像へ発音群ごとの節点を置いて実時刻列を移し替えることも禁止する。発音群数と同じ長さの楽譜間隔または実時刻列を持つ負対照は、診断には使えるが採用候補にしない。

### 固定候補族

未知のbeam searchを導入せず、次の直積27候補をすべて評価する。

- 発音群3種: 30 ms群、60 ms以内の単調な低音から高音への打鍵をrolledとして統合、同じ打鍵を別位置として維持
- 相対音価語彙3種: 二分、二分と付点、二分と付点と三連
- 共有時間写像3種: 1区分、4区分、8区分の単調な区分線形写像

30 msは既存診断の群幅、60 msは同時発音候補の上限であり、一般の時刻誤差許容値ではない。時間写像の節点数は区分数+1とし、最大9にする。

固定した時間区分内の尺度と音価列は、尺度の有限な切替点を走査して大域最小化する。分位点から始める局所的な交互更新は、収束しても最小解を逃す反例が確認されたため採用しない。時間区分境界まで動かす段階では、音価列と境界列の組が直前と同じなら収束、直前以外の既訪状態なら循環として`not_converged`にする。開発曲ごとに語彙、区分数、反復条件を変えない。全候補が完了した後にだけ、再構成差と各複雑さのPareto関係を診断する。一つの重み付きlossで採否を決めない。

観測時刻コピーと等間隔格子も、通常候補と同じく、発音群参照、時間写像節点、局所打鍵差を含む表現として直列化サイズを測る。楽譜位置列だけを測って通常候補より不当に小さくしてはならない。通常候補が観測時刻コピーより再構成差で劣っても、直列化サイズを減らし、等間隔格子より再構成差を改善していれば、有効なトレードオフ候補として診断する。この診断だけで採用候補を一つに決めない。

全観測時刻から音価と境界を決めた後、一部の時刻だけを線形当てはめから除いた値は、独立した保留評価ではない。`withheld_anchor_mean_error_us`という旧名は廃止し、`in_sample_interpolation_error_us`として診断にだけ使う。候補方式の採否は、既知生成元の正解位置比、真のレンダラー時間写像、方法固定後の保留曲を根拠にする。

既知生成元ではScoreSpecを探索入力にせず、推定後にだけ全体倍率を除いた楽譜位置比と比較する。参照曲には正解譜がないため、循環再構成を元譜の復元成功とは呼ばない。

### 既知生成元ゲートの結果

固定時間区分の音価探索を大域化した結果、既知生成元6例の完全復元は0例から4例へ増えた。したがって、初期失敗の主因の一つは中間表現の不足ではなく、局所探索だった。

残る`multiscale-v5`は372区間中9区間だけが異なり、不一致は区間270から278へ連続している。既知楽譜位置を固定した診断では、8区分の境界を等間隔から可変にすると平均アンカー誤差が129,551 usから31,178 usへ下がり、境界270が選ばれた。可変境界と音価を交互更新する8区分候補は、この例を完全復元した。一方、4区分候補は16状態を巡回して`not_converged`になった。

別系統の`reference-variance-v7-a2`は、60 ms以内の上行分散和音を統合した発音群だけが既知楽譜と両立し、固定境界の最良位置比一致率は0.79651163だった。4区分と8区分、3音価語彙の可変境界6候補はすべて完全復元せず、最良一致率も0.52906977へ悪化した。全失敗例へ可変境界候補を追加したrunnerは7分を超えて完了せず中断した。このため、可変境界は常用候補へ採用しない。

反復素材の音価共有も採用しない。固定境界の不一致は、反復する`material_1`と`material_2`の各出現内部にはなく、`material_3`、`material_5`、`material_6`など別素材と区間境界に分布していた。反復素材へ同じ音価列を課しても失敗箇所を変えられない。

区間ごとに音価語彙と尺度を選ぶ局所リズム格子も採用しない。区間内の音価比だけを比較する診断では、人工対照5系統の完全一致区間が63から94へ増えた。一方、未解決の`reference-variance-v7-a2`では完全一致区間が4、音価比の一致が51/162のままで、全11区間が大域候補と同じ結果だった。異なる区間尺度を連結して曲全体の楽譜位置へ戻す根拠もない。したがって、ScoreTimingだけへ局所補正を重ねず、有限のScoreTiming候補を素材と構成の仮説まで保持し、上位の反復、境界、声部情報が候補を絞れるかを次に反証する。

音高形の反復と対応する楽譜間隔比を候補ごとに集計した結果、既知生成元6例、独立2系統のすべてで、同じ発音群でもScoreTiming候補によって診断値が変わった。完全復元候補と不正解候補が同じ診断値へ潰れた例はなく、完全復元候補がない2例でも、最良一致候補はより悪い候補と同じ診断値へ潰れなかった。したがって、有限候補を上位層まで保持する価値はある。

ただし、反復する音高形で同じ音価比になる割合を最大化する単純規則は、6例中2例で既知最良候補を外した。この規則は採用しない。候補の区別が可能であることと、観測だけから正しい候補を選べることを混同しない。独立系統も2つしかないため、選別規則を作る前に、既存成果物から独立した既知生成元を増やせるかを調べる。

`.appendix`の77最上位ディレクトリと91件の`run-state.json`を棚卸しした。既存6例は証跡種別別の検証を通り、既存の2系統を維持した。91件のrun-stateのうち、現行のPiecePlan、ScoreSpec、PerformanceSpec、最終SMFがそろい、completed-run検証を通ったものは、登録済みの`reference-variance-v7-a2`だけだった。残る90件は必要な3段階IRの一部または全部がなく、追加対照にできなかった。

attempt配下には102件のアクセス拒否があり、棚卸し全体は`partial`である。ただし、確認できたrun-stateと各run直下の成果物には、新しい明示的`group_id`を持つ検証済み候補はなかった。ファイル内容やディレクトリ名から独立系統を推測せず、選別規則を検証する前に、異なる構成、音価、演奏時間を持つ既知生成元fixtureを新たに複数用意する。

### 人工既知生成元の契約

既存成果物を別名で水増しせず、現行のPiecePlan、ScoreSpec、PerformanceSpecから決定的な4設計族を生成する。LLMは使わない。3例は音価語彙内、1例は音価語彙外の負対照とする。人工例は推定方法の反例検査にだけ使い、参照232曲や利用者の作風への一般化証拠には数えない。

各例は32発音間隔、33発音位置を持つ。8間隔のcycleを4回並べ、第1から第3cycleは音高templateの先頭8群、第4cycleだけ終止群を含む9群を使う。これにより、cycle境界へ同時刻の発音を重複させない。各例の音価cycle、構成木、音高template、演奏profile、候補内外の期待は、実行結果を見る前に版付き定数へ固定する。

設計族は次の5成分を別々に比較する。

1. 構成木形。
2. 全体倍率を除いた隣接発音間隔列。
3. 既知楽譜と両立する発音群profile集合。
4. 葉順のtiming、amount、coordination profile列。
5. 同一ScoreMaterialまたは`derived_from`による反復関係。

ID、title、絶対移調、目標時間、velocityは設計族の差に数えない。各新例は、既存2系統とほかの新例のそれぞれに対し、5成分中3成分以上が異なることを要求する。ただし、これは人工対照の重複防止であり、実在曲としての統計的独立性を意味しない。

各builderは3段階IRと`KnownTimingSource`を返す。保存時はDSL往復、SMF再読込、全note-on対応、semantic lineage、再生成の決定性を検査する。発音群の両立、音価語彙への所属、全体倍率を除いた楽譜位置比の復元、真のrenderer時間写像への近似を別の結果として記録し、一つの`recovered`へまとめない。候補外の設計意図と、探索後の実測状態も別フィールドへ保存する。

`rolled-nested-recurrence`は三連を含む音価語彙内だが、`narrative-v2`のcycle内部の非線形な時間揺れと音価推定が交絡し、固定27候補では32区間中28区間一致にとどまった。この例を成功例へ直すためにfixtureを変更しない。音価語彙内だが候補全体では復元できない時間写像の負対照として保存する。したがって、新4例は、候補全体で復元できる2例、時間写像との交絡で復元できない1例、音価語彙外の1例になる。

### TextureGraph採用前の圧縮edge診断

ScoreTimingの次で、最高音を主旋律、最低音をbass、生成IRの`upper/lower`を左右の手または知覚voiceへ読み替えない。voice separation、melody identification、手の割当、生成IRの二値voiceは別の問題として扱う。

永続的な`TextureGraphHypothesis`型を作る前に、既存の発音群profileを参照する診断だけを実装する。発音群内容のhashをsemantic profile IDとし、同じ内容を持つ複数profile IDはaliasとして一つの診断へ向ける。診断はgroup indexとmember indexを使い、元event ID、絶対音高、絶対時刻、duration、velocityの全note表を再掲しない。

縦方向は同音高のmember index集合を順位blockとして表す。横方向は、隣接発音群間の最近傍関係を、始点と終点の順位block indexで参照する。同じmember index集合を横関係へ再掲しない。同音tieの完全二部edgeを一件ずつ列挙せず、実際に展開した場合の組合せ数だけを診断値として計算する。voice pathも物質化せず、曖昧性の上限だけを診断する。

初回の18曲診断では、表面上のgrouping profile 54件を内容が異なる34件へまとめ、ScoreTiming候補486件に対してbase graphを34件だけ作れた。全34件でevent IDを再掲せず、2回の実行成果物もバイト単位で一致した。一方、診断JSONは元のgrouping JSONの0.91倍から4.42倍だった。主因の一つは、横関係が順位block indexに加えて、そのblockのmember index集合も再掲していたことである。この冗長性は上位仮説に必要な情報ではないため、永続型の採用判断前に削除して再測定する。

再測定後も、texture診断JSONの合計は3,405,542 bytesであり、grouping JSONの合計1,547,665 bytesの2.20倍だった。18曲中17曲でtexture診断の方が大きい。縦順位と最近傍関係は、groupingとObservedPerformanceの音高から決定的に再計算できる。現時点ではconsumerも確定していないため、base edgeを永続的な仮説型へ保存しない。上位処理が必要とする間だけ計算する派生viewとし、永続型にはvoice候補、代替、仮定、確信度など、入力から一意に導出できない情報だけを残す。

18曲を処理できたという`pass`と、仮説型の採用条件を満たしたという判定を分ける。曖昧性の上限、ScoreTiming fingerprintの候補識別、voice対照、consumer契約、再現性を個別に検査し、未確認項目があれば採用状態を`pending`または`rejected`にする。

base edge診断はsemantic groupingごとに共有する。ただし、同じ発音群でもScoreTiming候補により楽譜間隔比の意味が変わるため、候補別の軽量なfingerprintを別に結合する。base graphを27個へ複製しないことと、Textureの意味がScoreTimingから独立であることを混同しない。

既知`ScoreNote.voice`は観測診断を凍結した後だけ使う。人工4fixtureは最高音を`upper`へ割り当てる同じ生成規則を持つため、voiceの独立4設計族とは数えず、音高順位oracleの循環対照とする。既存生成元にも音高順位から独立した反例が不足する場合、永続型を採用せず、既知voice fixtureを別に設計する。

### 最近傍関係と生成元ラベル比率の対照

既存6件、2設計族では、最高音または最低音の単純規則に反する生成元`upper/lower`ラベルを確認済みである。新しいfixtureを先に増やさず、次に、相互最近傍関係がラベル構成だけで生じる一致率を上回るかを記述的に測る。

隣接する発音群`G_t`と`G_(t+1)`について、両群の全memberの直積に含まれる同ラベル組の割合を区間ごとに求める。各区間の割合を、その区間で相互最近傍関係が展開するvirtual pair数で重み付けした値を`matched_pair_weighted_null_same_label_rate`とする。相互最近傍virtual pairの実測同ラベル割合を`mutual_nearest_same_label_rate`とし、後者から前者を引いた値を`same_label_rate_lift`とする。これにより、両者の区間別の重みと分母を一致させる。全member直積を一括した`adjacent_all_pair_same_label_rate`は補助的なpooled値として残すが、liftの基準には使わない。個別pairは成果物へ物質化せず、同ラベル数と全pair数だけを集計する。

この対照は、同じ隣接群と同じ`upper/lower`構成のもとで、音高近接によるpair選択が同ラベルを多く結ぶかだけを測る。liftが正でも、旋律線、知覚voice、左右の手、前景、伴奏を回収した証拠へ読み替えない。source間の独立性と標本数が不足するため、普遍的な閾値や統計的な合否を設けない。同じ設計族の版違いは独立した設計族として数えず、source件数と肯定対象の設計族数を併記する。

3種類のgrouping profileをすべて評価し、同内容だけをsemantic aliasとしてまとめる。既知生成元のうち、`rolled` coordinationは`ScoreNote.voice`から打鍵順を作るため、これを含むsourceの値は記述用に残すが、oracle非依存の肯定証拠へ数えない。`oracle_basis`はgroup IDの命名規則から推測せず、source metadataへ明示する。

この診断結果だけから、永続的なvoice表現または`LineAndHarmonyHypothesis`のconsumer契約を採用しない。次段階では具体的なconsumerとScoreSpec候補へのadapterを先に定義し、実際に読まれる非導出情報だけを検討する。

### 前景・和声・伴奏の候補型を作る前の支持診断

前景、和声、伴奏を一つの直積状態として列挙しない。素材境界が空の曲では、全memberの二値役割と48和声を組み合わせるだけで候補数が実用範囲を超える。また、全memberへ`foreground|accompaniment`を許す因子表現は、任意の生成元ラベルを必ず代入でき、収容力検査が空疎になる。

前景については、既存のtexture edge診断を再利用する。最高音、最低音、相互最近傍関係は生成元`upper|lower`と相関しても、知覚上の前景、伴奏、左右の手を安全に除外できるhard constraintとは扱わない。同一voiceの複数同時音、声部交差、継続証拠なしを別々に記述し、除外規則が成立しない場合は`unresolved`を維持する。

和声についても、観測音と一音以上共通する和声だけを残すhard domainを作らない。観測音高クラスを増やすほど該当和声の集合は単調に拡大し、候補削減の向きと一致しないためである。さらに、持続する和声音上で前景の非和声音だけが続く場合、現在打鍵音または固定長の発音群窓から真の和声を除外できる。

現行正方向語彙の12根音と`major|minor|diminished|major-seventh`、合計48和声を固定し、各発音位置で次の二つを独立した支持量として保存する。

- `attack_support`: 30 ms発音群で新しく打鍵された音の構成音数、非構成音数、構成音率。
- `key_held_support`: 発音群開始時に`onset_us <= group.onset_us < offset_us`を満たす押鍵中音の構成音数、非構成音数、構成音率。

major-seventhは三和音より構成音が一つ多いため、構成音数だけで比較せず、分母と和声構成音数を併記する。一つの重み付きloss、順位、閾値、hard domainへ変換しない。低音域MIDI 48未満では、根音・完全五度、第三音、その他を分けるが、禁止条件にはしない。

`key_held_support`は鍵盤が押されている範囲だけを表す。CC64でnote-off後も鳴る音は、channel別のペダル状態、同tick内のevent順、同音再打鍵を含む追加契約が必要なため、この診断へ混ぜない。note対応が曖昧なsourceでは`key_held_support`だけを`unable_to_investigate`とし、`attack_support`やsource全体を0件へ変換しない。

三発音の半音または全音による形は、音価条件を持たない限り`stepwise_motion_evidence`と呼ぶ。正方向契約のpassing toneまたはneighbor toneへ読み替えない。

観測runはSMFだけを読み、入力、規則、コード、出力のhashを凍結する。oracle runnerは凍結済み観測成果物のhashを確認した後だけ既知ScoreHarmonyを読む。生成元`upper|lower`とScoreHarmonyは候補生成に使わず、支持量の記述診断に限る。

参照232曲のroundtrip SMFは、`manifest.json`から`roundtrip.jsonl`を検証し、各レコードの`regenerated_sha256`からSMF実体を検証する二段経路で入力を証明する。`run-spec.json`のsource hashは元SMFのhashであり、roundtrip実体へ直接照合しない。

この診断だけから、前景・和声・伴奏の永続候補型を採用しない。観測支持が候補を一意にしない場合は、正方向の段階生成で複数案を作り、支持量、ScoreSpec validator、一般品質、候補間比較で選ぶ方式を次に検討する。

#### 診断結果と採用判断

既存texture証跡では、生成元voiceラベルに依存せず肯定証拠へ数えられる5件は同じ設計族の改版だった。最高音と`upper`の一致率は0.7265から0.7280、最低音と`lower`は0.7474から0.7507だった。相互最近傍の同一ラベル率はnull率を0.3752から0.3875上回った一方、同じvoiceに複数の同時音を持つ発音群が各74件から79件あった。音高順位と近接には相関があるが、知覚上の前景または伴奏を安全に除外できる証拠ではない。前景と伴奏のhard分離は`unresolved`とする。

和声診断は、既知生成元6件と和声未宣言の人工4件、参照232曲へ同じ規則を適用した。既知生成元の宣言和声2,055群について、`attack_support`で宣言和声が単独首位になった群は0件、同率首位は2,021件、ほかの和声より支持が低い群は34件だった。`key_held_support`を比較できた1,291群も、単独首位0件、同率首位1,291件だった。残る764群は押鍵中音の対応を比較できず、0件へ変換していない。

参照232曲は全件を処理し、141,374発音群を評価した。新規打鍵音と一音以上共通する和声は、最小でも48候補中13候補残り、全48候補が残る発音群も5件あった。押鍵中音でも、評価可能な140,868群で最小13候補が残った。単純な観測支持は和声候補を十分に絞らず、既知和声の順位付けにも使えない。

以上から、`CoupledScoreFactorsV0`などの前景、和声、伴奏を連成した永続候補型は作らない。二つの和声支持量は診断用の派生値として残すが、hard domain、順位、lossへ使わない。逆分解から一つの正解を作るのではなく、正方向で構成、和声骨格、前景、伴奏、演奏を段階的に提案し、既存validatorと複数候補比較で不成立案を落とす方式を次の設計対象とする。参照SMFの観測特徴は、正解ラベルではなく、分布、制約、比較材料として利用する。

### 正方向候補アダプターのcoverage監査

`PiecePlan`、`ScoreSpec`、`PerformanceSpec`を構成する54フィールドについて、SMFから得る値の出所、元データとの対応、アダプターの処理、値を読むconsumer、確認済みの証拠を分けて監査する。単一の「復元済み」フラグへまとめない。

一致条件もconsumerごとに分ける。

- 基本検証器を通ること。
- MusicXMLへ楽譜上の意味を保って出力できること。
- `RenderedPerformance`のnote-on、note-off、velocity、CC64、node intervalを再現できること。
- SMFの観測イベントを再現できること。
- 段階DSLとsemantic lineageを再現できること。
- 汎用品質ゲートを通ること。

単一素材、音価1、音高順位によるvoice、和声なし、中立的な演奏指定を補えば、67音の骨格は基本検証器を通り、音数と音高を保ったMusicXMLとSMFを出力できた。しかし、これは再合成の成立を意味しない。9節点の共有時間写像を持つScoreTiming候補は、現行`PerformanceSpec`の有限なprofile語彙へ直接格納できない。中立指定で再出力したnote-onは、元SMFに対して平均459,701.493 us、最大1,116,000 usずれた。汎用品質ゲートも、構成、対比、終止、和声、尺、終止音価、ペダルの8条件で不合格だった。

音の長さは`ScoreNote.duration_units`だけでは決まらない。ScoreNoteのarticulation、PerformanceSpecのarticulation profile、rolled coordinationがnote-onとnote-offを変える。velocityもdefault velocity、dynamic direction、accent、dynamics profileの組で決まる。ペダルを含む実際の発音終了はkey-held note-offとも異なる。したがって、duration、articulation、coordination、velocity、pedalを別々に確定した後で結合する直列復元は採用しない。

最初の欠損は、もっとも成熟しているScoreTiming候補でさえ現行`PerformanceSpec`へどう写すか未定なことである。次は新しい型を直ちに追加せず、既存のtiming profileとtiming amountが、複数の既知生成元の共有時間写像をどこまで表現できるかを有限探索で反証する。表現できない場合にだけ、共有時間写像を正方向契約へ追加する設計変更を検討する。その後に、音価、articulation、coordination、pedalを連成した段階へ進む。Line、Harmony、Formの仮説を先に増やさない。

### ScoreTimingとPerformanceSpecの確定時期

構成を使わないroot兼leafの単一nodeと、最後の発音後を1 unitだけ残す限定条件では、現行PerformanceSpecの30表記は13種類の共有時間写像になる。人工既知生成元4設計族の固定108候補のうち、楽譜位置が既知譜と両立した21候補をこの限定条件で評価し、18候補が最大1,000 us以内だった。残る87候補は、楽譜位置不一致69候補と発音群不一致18候補へ分けた。上流で不一致の候補をPerformanceSpecの表現不足へ数えない。

単一nodeの結果をPerformanceSpec全体の表現範囲とは扱わない。rootとleafのprofileを平均合成した固定反例は、単一nodeの13写像に含まれず、最良写像でも最大402,000 usずれた。また、発音位置を0から100、profileを`savor/moderate`へ固定して素材長だけを101から151へ変えると、両端を合わせた内部写像も変わった。長い素材の写像を、短い素材で使える全30表記へ当てた最良値も最大807,148 usであり、1 tick相当の1,000 us以内へ入らなかった。

したがって、ScoreTiming候補を構成木と末尾音価より先にPerformanceSpecへ確定しない。時間profileは親子nodeで合成され、最後の発音より後の素材長も発音前の写像へ影響するためである。次段階では、ScoreTiming候補を保持したまま、素材境界、構成木、最後の発音後の長さを扱う。未知のnodeを時間誤差の吸収だけを目的に追加してはならない。共有時間写像を新しい正方向フィールドへ追加するかは、構成と末尾音価を得た後でも現行語彙に収まらない例を確認してから判断する。

局所打鍵差は共有時間写像と分ける。全offsetが0の候補は`score`と`aligned`、現行rendererの整数ms丸めを含む低音から高音への最大45 msのoffset列は、音高順位voiceという人工fixture固有の仮定付きで`rolled`へ写せる。それ以外は現行coordination語彙で未表現とする。既知内部node境界は候補写像の定義域内だけcharacterizationできる。最後の発音より後にあるroot終端は評価不能であり、構成復元の証拠へ数えない。

### 構成と素材境界の同定可能性

構成木と素材境界を推定する前に、同じSMFを生成する異なる潜在IRを固定変換で作った。対象は、5成分基準で異なる4つの人工設計族である。これらは統計的に独立した4曲ではなく、反例のfixtureとしてだけ扱う。

変換ごとの結果は次のとおりである。

- 反復注釈の消去は、適用可能な3設計族すべてで同一SMFになった。
- 演奏指定を持たない内部nodeの平坦化は、適用可能な2設計族すべてで同一SMFになった。
- 中立条件を満たす隣接素材の結合は、適用可能な2設計族すべてで、素材数と境界が変わっても同一SMFになった。
- `ScoreSpec.divisions`だけの倍化は、4設計族すべてで同一SMFになった。
- divisionsと全unit fieldの倍化は、3設計族で同一SMFになった。非線形な打鍵分散を持つ1設計族は、中点の再標本化により最大1 msだけ異なった。
- 最初のnoteを1半音上げる破壊対照は、4設計族すべてで差を検出した。

同一SMFになった比較でも、木形、素材境界、反復注釈、素材数、node interval、lineage、provenanceのいずれかが異なる。したがって、SMFから元の構成木、素材境界、`derived_from`、絶対的な楽譜単位値を普遍的に一つの正解として復元する設計は採用しない。

一方、この結果は構成や素材境界が不要であることを意味しない。反復する音形や演奏上の変化から、生成に役立つ候補を立てることはできる。次の段階では単一の`FormHypothesis`を確定せず、同じ観測を説明する代替候補、各候補を選ぶ仮定、候補間で共有できる情報を持つ最小表現を先に定める。

全体尺度を除いた終端までの比率と、最後の発音後に必要な演奏時間は、この反例では決まっていない。これらを絶対unit値の非同定性と混同せず、構成候補と連成した未解決事項として残す。

### 構成同値候補の実験契約

`CompactStructureDescriptorV0`と`StructureEquivalenceSetV0`は採用前の実験型である。既知生成元だけを使い、同一SMFを説明する構造差を失わず保持できるか、候補閉包が有限かを調べる。実在曲から候補を発見できること、候補を順位付けできること、作風へ一般化できることは、この実験の成功条件に含めない。

`CompactStructureDescriptorV0`は次を持つ。

- root終端を1とする有理数のnode spanとmaterial出現span。
- node種別、正規化した親経路、兄弟順、同一span内ordinalから作る局所ID。
- nodeの親子関係。
- `subject_kind=node|material`を持つ`derived_from`関係。
- materialごとの出現leaf集合。
- 最後の発音からroot終端までの正規化比率と、観測、候補仮定、oracle、未解決を分ける状態。
- 絶対unit尺度を消した正規化ID。

音高、velocity、durationの全表、生event列、全発音群member、元IRのIDは保持しない。4つの人工fixtureに正例がない`contrasts_with`はV0へ含めない。将来追加する場合は正例と破壊対照を先に用意する。

同じspanを持つ単項内部nodeとleafを、spanだけで同じ要素へ潰さない。node由来とmaterial由来の`derived_from`が同じspan対を結んでも、`subject_kind`で別関係として保持する。単位尺度だけが異なるIRは同じ正規化descriptorへまとめる。

`StructureEquivalenceSetV0`は次を持つ。

- event ledgerのSHA-256と30 ms発音群規則の版。
- `matched_candidate`、`outside_candidate_space`、`oracle_only`を分けるScoreTiming依存状態と、実在する場合だけ候補IDの集合。
- 検証済みの`CompactStructureDescriptorV0`の明示的な集合。
- 候補間の対象付き変換edgeと、その仮定、根拠状態。
- 一回限りの単位尺度対照。
- `source_kind=oracle_coverage_fixture`。

候補差分を自由に組み合わせる暗黙の直積は作らない。対象付き変換後に基本validatorを通り、開始点と同一バイトのSMFを生成した候補だけを列挙する。node関係の消去、material関係の消去、内部nodeの平坦化、隣接素材の結合は、関係数、内部node数、素材境界数の合計を必ず減らす変換に限定する。尺度倍化は無限に反復できるため閉包作用素に含めず、各構造候補への一回限りの対照とする。

明示候補方式を先に反証する。差分patch型、BDD、探索DSLは、候補数または直列化量が実測上の問題になるまで追加しない。候補閉包が収束しない、必要な構造差を失う、生note列の複製が必要になる場合は実験型を採用しない。

既知IRはdescriptorの収容力と正方向再生成の事後評価だけに使う。候補の発見、順位、確信度へ混ぜない。ScoreTiming候補空間で既知位置を回収できないfixtureは、候補IDを補わず`outside_candidate_space`とし、spanがoracle由来であることを明示する。

### 構成同値候補の実験結果

4つの人工設計族で、対象を指定した単調な構造変換の閉包を求めた。候補数は`binary-aba-aligned`が22、ほかの3設計族が各8であり、合計46候補、81変換edgeになった。各fixtureの候補数は、初期IRの関係、内部node、素材境界から導いた素朴上限64、64、64、8以下で、新しい候補がなくなるまで収束した。

全81edgeでvalidator合格、元fixtureとのSMF byte一致、構造測度の減少、edge端点の存在と全候補への到達可能性を確認した。候補IDとdescriptorのSHA-256、JSON往復、候補の出所、ScoreTiming依存、尺度対照の一対一対応、終端値、禁止情報を含む48契約検査もすべて合格した。pitchを1半音変えた4破壊対照では、構造descriptorを保ったままSMFとevent ledgerの差を検出した。

明示descriptorの合計は57,282 bytesだった。候補数46件の段階では実用不能な量ではないため、差分patch型やBDDは追加しない。nodeの`role`は現行consumer根拠がなく候補識別にも寄与しなかったため、V0から除外した。material再利用は、同じ素材を2つのleafから参照する小対照で、出現集合を失わないことを確認した。

各単独runの採用状態は、再現性を自己証明したことにしないため`pending_repeat_comparison`とした。初回と再実行の5成果物を外部比較し、すべてバイト単位で一致した。この結果から、`StructureEquivalenceSetV0`を既知生成元に対する収容力検査の実験型として採用する。ただし`source_kind=oracle_coverage_fixture`の範囲に限る。実在SMFから素材境界、反復、階層の候補を発見した証拠にはならず、候補順位と確信度も未実装である。

最後のnote-off、最後のCC64 off、end_of_trackは観測値として分離できたが、作曲上の終端は`unresolved`のままである。候補上の最後の発音位置とroot終端の比率は`assumed_from_candidate`であり、SMFから回収した事実とは扱わない。

### 素材境界・反復の観測候補契約

`ObservedStructureCandidatesV0`は、実在SMFから構成木を確定する前の実験型である。固定済みの開発用8曲と各27個のScoreTiming候補を入力にし、素材境界と反復関係の有限候補を作る。既知の楽譜、構成ラベル、生成元IR、material ID、node IDは候補発見へ使わない。保留標本は方式を凍結するまで物質化しない。

同じ発音時刻、元event ID集合、群内相対発音時刻の列を持つgrouping profileは、canonical hashが同じsemantic profileとしてまとめる。表面上のprofile IDは来歴にだけ残す。境界anchorは、semantic profile hash、前後の元event ID集合、前後の発音時刻で表す。曲全体へ一つのgroup indexを仮定せず、件数と選択率はsemantic profile別に測る。

境界の観測信号は次の三族を分ける。

- 休止: 対象の発音間隔を、対象を除いた左右近傍の正の発音間隔の中央値で割る。局所中央値以下は候補にしない。
- テクスチャ: 左右近傍における全音高、発音群内音数、鍵盤を押している時間の中央値差を、曲全体の各特徴範囲で正規化して平均する。発音間隔を重ねて使わない。
- 反復端点: canonical反復候補の開始と終了を使う。検索上限で打ち切られた側の端点は使わない。

近傍幅は4、8、16発音群とし、左右がそろう尺度だけを使う。各尺度の局所最大を生候補にする。同値が連続する場合は一つのplateau範囲として保持する。尺度間では範囲が交差する候補だけを統合する。同じ族の複数尺度を独立した証拠として数えない。

初回V1は異なる二族が重なる位置を最終境界とした。しかし長い3曲では、3～8発音群の短い反復端点が内部位置の90%以上を覆い、最終境界の選択率が0.69～0.73になった。反復候補は存在しても、素材境界を選ぶ証拠としては選別力を確認できなかった。V1は不採用とし、V2では休止とテクスチャの両方が重なる位置だけを最終境界とする。反復端点はオンデマンドの診断として残し、採否には使わない。この変更は開発8曲を見た後の変更なので、開発結果をV2の採用証拠に数えない。

反復候補は、最高音、最低音、最低音基準の音程集合という三つのpitch viewを使う。音高形は全体移調に不変とし、ScoreTiming候補ごとの発音間隔比は最大公約数で正規化する。3発音群から8発音群の非重複一致を対象にし、上限内で最長の一致だけを残す。長さ8では左右への伸長可能性を別々に記録し、伸長側の内部端点を境界証拠にしない。pitch viewは同じ音列の投影であり、別の証拠族として数えない。

同じfingerprintの出現集合は一件へまとめ、全出現対を保存しない。生event列と全note列も上位成果物へ複製しない。発音群内容、score position列、境界anchor、反復fingerprint、出現anchor、相対リズム分類が同じScoreTiming候補だけを同一aliasにする。

V1の上位JSONは20,205,317 bytesで、下位ScoreTiming JSONの4,349,287 bytesを超えた。主因は、反復出現の冗長なフィールド、全eligible edgeへの候補ID列、点境界の同一anchor二重保存だった。V2 schemaはversion 2とし、次のlosslessな正規化を行う。

- 反復出現は、semantic profile内の開始group indexと左右の伸長状態を持つtupleにする。終了位置と境界利用可否はwindow sizeから導出する。
- window size、出現start集合、伸長状態が同じpitch viewを一候補へまとめ、view別pitch shape hashを保持する。
- 点境界は単一の`anchor`だけを持つ。
- 全eligible edgeの反復支持集合は保存せず、同じ成果物のcompact反復候補から導出する。
- ScoreTiming aliasは、`source_sha256 + candidate_id`を下位join keyとし、候補IDの所属を保持する。score position列とリズム分類は検証済み下位成果物から再結合する。
- pair件数は出現startとリズム分類から導出する。

V2 decoderは、V2成果物とhash検証済みの下位ScoreTiming JSONだけから、alias所属、score position列、リズム分類、全eligible edgeの支持集合を復元する。元SMF、V1成果物、抽出器の再実行を復元へ使わない。V1とのmigration testではcandidate IDを比較せず、view、pitch shape hash、window size、出現start、伸長状態のcanonicalな意味を比較する。

`boundary_status`と`recurrence_status`は独立させる。候補があれば`assessed`、観測証拠がなければ`insufficient_evidence`、入力または対応を検査できなければ`unable_to_investigate`とする。境界候補がなくても反復候補を捨てない。

V2の採用条件は次とする。

- 観測信号を埋め込んだ肯定対照で、意図した境界anchorと完全一致する。
- 固定済み開発8曲を同じ規則で処理し、境界と反復がそれぞれ2曲以上で`assessed`になる。
- `boundary_status=assessed`の各semantic profileで、候補範囲が覆う内部位置の割合が0.5以下になる。
- 上位候補JSONが検証済みの下位ScoreTiming候補JSONより大きくならない。
- 全体移調で候補を保持し、音高payloadの順序変更と発音間隔列の回転を、安定した元group IDで比較して検出できる。
- 同じ入力による2回の成果物がバイト単位で一致する。

V2では開発8曲を既知不具合の回帰確認にだけ使う。移調対照、境界選択率0.5以下、上位JSONが下位JSON以下を要求するが、採用証拠には数えない。設計、実装、テスト、候補定数、開発回帰をローカルcommitで凍結し、`.appendix/observed-structure-method-v2/method-manifest.json`へcommitと各SHA-256を保存する。

開発回帰では8曲すべてを処理し、境界候補と反復候補をそれぞれ7曲から得た。上位JSONは3,489,459 bytes、下位ScoreTiming JSONは4,267,061 bytesで、V1の容量超過を解消した。移調、音高順序、発音間隔回転、休止、テクスチャ、反復端点の対照は合格した。2回の実行で5成果物がすべてバイト一致し、V1とV2のcanonicalな反復関係も8曲すべてで一致した。この結果は既知不具合の回帰確認であり、V2の採用証拠ではない。

凍結後に、既存のlocal neighborhood規則で未使用の保留8曲を一度だけ選ぶ。保留を物質化した時点で、合否にかかわらず将来方式の採否には再利用しない。同一凍結方式の決定性再実行だけを許容する。V2の採否は保留8曲で判定する。境界と反復がそれぞれ2曲以上で得られ、各境界選択率が0.5以下、上位JSONが下位JSON以下、三破壊対照と三肯定対照が合格し、再実行がバイト一致することを要求する。

commit`6d63055860bc3ad33a035dee700fcfed9ae5bc66`で方式を凍結した後、未使用の保留8曲を初めて物質化した。保留8曲すべてで境界候補と反復候補を得た。上位JSONは5,031,390 bytes、下位ScoreTiming JSONは6,805,804 bytesで、境界選択率、三破壊対照、休止・テクスチャ・反復端点の肯定対照も合格した。再実行の5成果物はすべてバイト一致した。したがってV2を、正解構成ではなく次段へ渡す有限候補器として採用する。

開発、保留、人工既知生成元を同じ候補生成器で扱うため、staging manifestは`split_role=development|holdout|known_fixture`と`staged_smf`を持つ。既存の`development_smf`は`split_role=development`として後方互換で読む。各runnerは成果物作成前と保留集計時にmethod manifest、凍結commit、宣言ファイルの実hashを照合し、不一致なら出力しない。

方法凍結では、境界・反復候補器だけでなく、SMF観測、ScoreTiming候補、参照profile距離、保留選択、既知構造staging、oracle adapter、関連テスト、依存定義を宣言ファイルへ含める。保留と人工既知生成元のrunnerは、検証済みmethod manifestがなければ実行しない。開発runnerだけは、凍結前の回帰確認との後方互換のためmanifestなしで実行できる。

人工既知生成元は、raw ScoreTiming、raw観測候補、oracle比較を別成果物にする。oracle adapterは観測抽出器から呼ばない。比較状態は`candidate_aligned`、`oracle_mapped`、`unable_to_compare`を分け、構成同値集合外を偽候補と断定しない。

oracle比較V1は、ScoreTimingの先頭発音と最終発音を`0`と`1`へ写した。しかし構成同値descriptorの`1`はroot終端であり、最終発音から後の終止余白を含む。この座標不一致があるため、V1の境界関係集計は不採用とする。raw ScoreTimingとraw観測候補は変更せず、比較器だけをV2へ上げる。

oracle比較V2は、oracle段階だけでhash検証済みの`piece-plan.dsl`と`score-spec.dsl`を読み、既知生成元の先頭発音と最終発音のroot内位置を再計算する。ScoreTiming位置は、この二点を端点とするアフィン変換でroot座標へ写す。baseline DSLから再計算したdescriptor、`origin_status=oracle_fixture_baseline`のdescriptor、全候補の`terminal_tail_ratio`が一致しない場合は`unable_to_compare`とする。

発音群列の終端はroot終端とみなさない。反復occurrenceの右端が発音群列の終端へ達する場合は、`end=null`、`endpoint_status=terminal_endpoint_unobservable`として保存する。同じ反復候補内の比較可能なoccurrenceは残す。aliasの`mapping_status`、境界の`oracle_relation`、反復occurrenceの`endpoint_status`は別々に保存、集計する。

oracle比較V2は、observed、timing、oracleのevent ledger、oracle manifest内のSMF hash、全source集合、入力manifest、凍結済み抽出method manifestを照合する。Git管理外の6入力はcommit済みの期待SHA-256へ固定する。比較器自身は、Git管理下の`src/llm_musical_composer/*.py`全件、依存定義、テスト、正本設計を別manifestで凍結し、そのmanifest hashを全評価成果物へ伝播する。過去の抽出方法は現在のHEADではなく、宣言した過去commitのblobで検証する。

V2比較を既知生成元4設計族へ適用した結果、41 aliasをすべてroot座標へ写像できた。境界320件のうち7件は列挙した全構成候補に共通し、313件は列挙集合外だった。反復occurrenceは2,093件の両端を写像し、63件の終端側を観測不能として分離した。2回の成果物はバイト一致した。この診断は有限候補器の採用条件ではなく限界の記録であり、列挙集合外を誤候補と扱わない。

人工既知生成元は方式を凍結した後の事後評価にだけ使う。単一の元IRを正解にせず、`StructureEquivalenceSetV0`の全候補に共通する境界、いずれかにある許容境界、列挙集合外を分ける。列挙集合外を偽候補と断定しない。反復も、観測上の音形反復と、保持または消去できるIR注釈を分ける。

この実験が合格しても、構成木、A・Bなどの区間名、素材の正解、候補順位、終端長、生成品質の改善は成立したと扱わない。

## 検証

### 生イベント往復

ObservedSmf から診断用 SMF を出力し、再読込した event ledger を比較する。バイト一致は要求しない。保持対象について、track、channel、絶対 tick、同時刻順序、message type、全フィールドの一致を要求する。

### 演奏対象往復

絶対時刻、note 対応、velocity、CC64 など、ObservedPerformance が扱う対象を比較する。生イベント往復と別に合否を返す。

### 既知正解対照

次の二種類を使う。

1. テスト内で既知の PiecePlan、ScoreSpec、PerformanceSpec からレンダリングした小さい fixture。
2. `.appendix/reference-variance-smoke-v7/runs/reference-a-candidate-2` の完了 run。

保存済み対照は `run-state.json` の完了状態、段階別 SHA-256、最終 SMF の SHA-256 を実ファイルと照合する。

### 破壊対照

- 全体移調
- 全体時間伸縮
- ペダル除去
- 区間順序の入替え
- 音高順の破壊

各対照で、変更対象と保持対象を別々に測る。一つの総合点へ合算しない。

## コーパスの扱い

第 1 段階では、`rut.mid` と `aimusic01.mid` を除く 232 曲すべてを ObservedSmf と ObservedPerformance へ変換する。開発標本と保留標本は使わない。

高い仮説層へ進む前に、観測済み特徴を使って開発標本と保留標本を固定する。その時点で、特徴群の集約、初期点、同距離時の順序、分割位置、被覆判定、copy fingerprint 群の扱いを定義する。保留標本の結果へ合わせた曲別規則を追加しない。

## 固定条件

- 参照 232 曲の全件状態を保存する。
- 失敗、調査不能、非対応を 0 件へ変換しない。
- 生観測と派生ビューを別の成果物へ保存する。
- 上位層へ生イベント列を複製しない。
- 同じ実装を全曲と既知正解対照へ使う。
- 現行の正方向生成経路を第 1 段階で変更しない。

## 可変条件

- 高い仮説層で保持する候補数。
- 開発標本と保留標本の大きさ。
- 仮説層で使う決定的分析または LLM。

可変条件は結果を見て曲別に変更せず、版付きの実行仕様へ固定する。

## 未解決事項

- 異なる既存曲から、同じ表現規則で有用な楽譜時間候補を抽出できるか。
- 声部、主旋律、伴奏、フィルインをどの確信度で推定できるか。
- 旋律と和声の相互依存を、候補爆発させず記述できるか。
- 素材再現と時間上の構成を、固定窓に依存せず推定できるか。
- 仮説から現行 IR へ戻したとき、意味のある部品交換ができるか。

## 停止条件

- 入力 manifest または SHA-256 が一致しない。
- 実在するイベント種別を黙って捨てないと往復できない。
- 既知正解対照の生成元と SMF の対応を証明できない。
- 上位仮説へ全 event 列を残さないと再合成できない。
- 保留標本へ曲別特例を追加しないと成立しない。

## 採用しなかった案

### SMF を直接 ScoreSpec へ変換する

同じ演奏イベントは、異なる楽譜時間、奏法、tempo map から生成できるため採用しない。

### 循環一致だけで成功を判定する

逆分解器と再合成器が同じ無意味な符号を共有しても合格できるため採用しない。既知正解、破壊、部品交換の対照を併用する。

### 一曲で全段階を先に作る

曲固有の構成と伴奏型を一般規則にする危険があるため採用しない。第 1 段階は 232 曲全件へ適用し、高い層では開発標本と保留標本を分ける。

### 第 1 段階で標本を固定する

PerformanceHypothesis の失敗様式が不明な時点では、保留標本が必要な条件を覆わない可能性があるため延期する。
