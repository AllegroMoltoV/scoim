# SCoIM設計の決定状態

この文書は、設計上の事項が「長期的に確定」「初版では確定」「仮置き」のどれかを一か所で管理する正本である。個別の設計書は現在の仕様を説明し、決定状態を重複して宣言しない。仮置きは勝手に確定へ昇格させず、実測または利用者判断を受けて本書を更新する。個別の設計書にある「値を確定する」「成果物を確定する」という表現は処理を表し、ここで扱う設計判断の状態とは区別する。

## 長期的に確定

- SCoIMは、短い作曲依頼から始め、人間とLLMが楽曲台本を介して即興曲を協創し、楽譜と演奏SMFを再現可能な形で生成するOSSである。
- 承認済みの楽曲台本を、後段の都合で黙って変更しない。
- 内容修正後は、同じ機械検査を先頭から再実行する。
- 内容修正を無制限に繰り返さない。
- 通信、認証、timeout、応答欠落と、応答内容の不合格を別の失敗として扱う。
- モデル要求、応答、検査、修正、結果を上書きせず保存し、試行を再検証できるようにする。
- 人間向けの表現と機械向けの表現は役割として分ける。
- 創作的な選択と、入力が同じなら結果も同じになる検査・変換を分ける。
- 自然言語で表した創作上の目標を、承認済みの観測方法なしに機械的な必須条件へ変換しない。
- LLM が選び、機械が実行する値は、選択した生成プロファイルが明示する有限な語彙に含める。
- 区分、マテリアル、マテリアル配置、楽譜生成単位、楽譜生成単位レイヤーを別の対象として保持する。
- 派生物は隣接する出所だけを参照し、同じ出所情報を複数段階へ重複保存しない。
- [前景](glossary.md#前景)と伴奏は[マテリアル配置](glossary.md#マテリアル配置)から判断し、上声または下声から推測しない。対応できない演奏方針を、声部単位の旧方式へ黙って読み替えない。

## 初版では確定

- 人間が通常確認するのは、楽曲台本と最終SMFの2か所だけである。
- 楽譜と演奏SMFを別の成果物にする。将来さらに分ける余地は残す。
- 一つの楽曲台本を一つの編成専用にする。
- Pythonで実装し、約3分の独奏ピアノとSMF出力を縦断する。
- LLMは音楽上の選択を、Pythonは現在定義済みの検査、参照、順序、長さ、配置、hash、保存、変換を担当する。
- `solo_piano_3m_v2`のフェーズ5では、LLMが伴奏音の和音度数と希望音域を選び、Pythonが全イベントを同時に配置できる具体音高を決める。最初に全音を希望音域内だけで探索し、上限へ達する前に配置不能と確認できた場合だけ、同じ和音度数を別の音域へ置ける。
- 楽曲設計データを作るフェーズでは、LLMによる構造、マテリアル、配置役割、再利用と遷移専用区分の提案、PythonによるID付与、能力検査と有効な遷移候補の列挙、LLMによる変奏、遷移候補の選択、自然言語の演奏指示の提案、Pythonによる参照構築の順に処理する。二つ目のLLMオペレーションは、一つ目で決まった構造と再利用を変更せず、遷移専用区分ごとにPythonが列挙した候補を一つ選ぶ。
- `solo_piano_3m_v2`の区分役割は識別子の形式だけを検査し、生成プロファイルの固定語彙またはPythonの音楽処理の分岐条件にしない。
- 遷移専用区分の指定には、区分役割とは別の非公開転送fieldを使う。遷移専用区分の全配置は、前景のマテリアル配置一つだけとする。遷移専用配置は、明示的な変奏関係の元または先にしない。
- 二つ目の構成オペレーションで上流構造の不足が判明した場合は、関係を捏造せず`structure_insufficient`で構成試行を失敗にする。
- 公開CLIの新規生成は`solo_piano_3m_v2`を既定値とし、`solo_piano_3m_v1`は明示指定する互換経路として残す。生成試行bundleの通信なし再生はmanifestの版へ振り分け、CLIの既定profileで旧bundleの意味を変えない。
- 初版の公開Python操作は、承認済み楽曲台本、構成bundle、生成試行bundleを扱う`realize`一つとする。`scoim`ルートには、`realize`と、その結果型、Codex用Runner、型付き問題に必要な名前だけを公開する。
- 公開v2生成の出力は、入力、profile、ID、[モデル実行条件](glossary.md#モデル実行条件)を持つ不変な識別記録と一体で初期化する。同じ識別情報と検証済み状態を持つ場合だけ再開する。
- 公開v2生成では、各モデル応答の[モデル実行条件](glossary.md#モデル実行条件)の一致を必須とする。Codex CLIから取得できないバックエンドの実モデル識別は、初版の必須条件にしない。
- v2生成試行bundleは、元の構成manifestのbytesとそのSHA-256を保存する。元の構成bundleがない通信なし再生では、元bundle内の全ファイルまで再検証したとは扱わない。
- `重なり`は初版の利用者向け制御に含めず、内部観測として扱う。
- `solo_piano_3m_v2`では、演奏指示から選ぶ演奏方法を生成プロファイルの演奏選択語彙に制限し、`scoim.performance_ir.PerformanceSpec`へ直接変換する。旧`v1`の同名型を新しい経路の中間型に使わない。
- `solo_piano_3m_v2`の演奏指示は、楽譜を変えずに調整できる時間の揺れ、強弱、音の保持、打鍵の揃え方、ペダルだけを扱う。音域、旋律、伴奏音、和音の要望は、区分とマテリアルの説明から楽譜生成段階へ渡し、演奏指示へ複写しない。
- `solo_piano_3m_v2`では、創作上の目標が意図どおりに聞こえたかを自動判定できなくても生成を続け、投影台帳と生成試行bundleへ`unverified`として記録する。これは失敗後の代替処理ではない。形式、安全、来歴、再現性、生成プロファイルの対応能力に不合格がある場合は生成を停止する。
- 内容修正を行う箇所では、元の依頼、不合格だったLLM応答、検査結果、変更禁止の上流値を渡して修正を求め、再検査する。
- 自動フォールバックは実装しない。修正しても合格しない場合は、理由を記録して失敗終了する。

## 仮置き

- 一曲を8フェーズで扱うこと。
- 楽曲台本と楽曲設計データを別のJSON文書として保存し、楽曲設計データの`source_flow`から元の楽曲台本を参照すること。
- 人間が将来どこまでの中間表現を見て編集するか。
- 初版後の実装言語と、LLMと決定的処理の個々の担当。
- 一つのLLMオペレーションに追加する内容修正を最大1回とすること。
- 公開`propose`で、修正可能なscalar fieldの置換値だけを追加1回求めること。
- 公開`solo_piano_3m_v1`の楽曲設計データ構築で、同じSchemaの応答全体を追加1回まで作り直すこと。
- 公開`solo_piano_3m_v1`の伴奏オペレーションだけに、応答全体の内容修正を追加1回まで行うこと。
- `solo_piano_3m_v2`のフェーズ2から5とフェーズ7で、各LLMオペレーションの内容修正を追加1回まで行うこと。
- `structure_insufficient`の後に新しい構成試行を自動で作る回数と停止条件。
- LLM呼び出し総数の上限を`2N`とすること。
- 内容修正でLLMへ返させる範囲と形式。伴奏段階では、同じSchemaによる応答全体の再提出を試運転値として使う。
- フェーズ4と6で診断用SMFを保存すること。
- 生成と修正に`gpt-5.6-sol`を使うこと。
- `solo_piano_3m_v2`で対応する[強弱方針](glossary.md#強弱方針)を`legacy-unison-v1`だけに制限すること。
- `solo_piano_3m_v2`では楽譜上の強弱と呼吸を生成せず、`ScoreDirection`を空にすること。演奏上の表情はフェーズ7の`PerformanceSpec`で扱うこと。
- `solo_piano_3m_v2`の演奏選択語彙に含める具体的な値と説明。
- `あかるさ`、`高さ`、`発音頻度`は、生成対照と知覚上の意味を確認できるまで公開Schemaへ接続せず、内部検証に限ること。

仮置きの値は現在の実装または次の小さな検証で使ってよい。ただし、公開互換性やSCoIMの恒久的な制約として扱わない。

## 現在の設計から外したもの

次の方式は、検証対象としてもいったん外す。過去の経緯はGit履歴、Beads、関連reportで確認する。

- 最初の検査で、すべてのblocking issueを列挙できなければ修正しない方式。
- すべての問題を最小のJSON leafまで特定できた場合だけ、後段の内容修正を許可する方式。
- 公開`propose`の限定実装を、後段全体へ一般化してLLMへleafの置換値だけを返させる方式。
- `validator-guided-local-repair-v1`を後段全体へ展開する計画。
- `solo_piano_3m_v2`のフェーズ6で、Pythonが終止音符を決定的に後付けする方式。
